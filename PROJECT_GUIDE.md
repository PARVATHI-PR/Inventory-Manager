# Inventory & Stock Manager — Project Guide

This guide explains the project in plain language: what each folder and file does, how the Java parts work together, how Oracle stores the information, and how a screen action travels between Java and the database.

## 1. What the project does

This is a desktop inventory program. A user signs in, then can view products and current stock. Depending on their role, they can also add products, manage suppliers and categories, record stock coming in or going out, view transaction history, and manage user accounts.

The program is built from three main pieces:

1. **Java Swing** displays the desktop windows, buttons, forms, and tables.
2. **Java business and data-access code** checks requests and sends database commands.
3. **Oracle Database** permanently stores users, products, suppliers, categories, and stock movements.

Java does not keep the main inventory data in a file or in memory. It asks Oracle for the latest data when it needs to display or change it.

## 3. How the parts communicate

The usual direction is:

```text
Person clicks or types in a Swing window
        ↓
UI class (LoginFrame or AppFrame)
        ↓
InventoryService checks the request and permissions
        ↓
InventoryDao builds and runs SQL through JDBC
        ↓
Database opens a connection using config/Database.java
        ↓
Oracle reads or changes rows
        ↓
Java maps the result to model objects
        ↓
Swing updates the screen
```

**JDBC** is Java's standard way to talk to a database. The Oracle JDBC driver (`ojdbc11`) translates Java's database requests into a form Oracle understands. Maven includes that driver in the finished application JAR.

The UI does not write SQL directly. That separation makes it easier to keep display code, business rules, and database work understandable and maintainable.

## 4. Java files and what they do

### Program entry points

#### `Main.java`

This is the normal application start. It asks Swing to open `LoginFrame` on Swing's event thread, selects the operating system's window style, and checks that the computer has a graphical desktop. It does not connect to Oracle itself; database access happens after the user attempts to sign in.

#### `BootstrapAdmin.java`

This is a one-time setup program, separate from the normal login window. It asks for an initial Admin username and password in a terminal. The password is hidden while typed, must be at least 10 characters, and must be entered twice consistently. It calls `InventoryDao` to save the account, then clears the password characters from memory.

The first Admin is needed because the database starts with role names but no user accounts. The bootstrap program does not create tables or role names; those come from the SQL setup scripts.

### Configuration and database access

#### `config/Database.java`

This class loads `config/application.properties` relative to the folder from which the program is started. It gets the URL, username, and password from environment variables first, if present; otherwise it reads the properties file. Environment variables take precedence.

`Database.connect()` creates a JDBC connection. If the optional `db.schema` / `INVENTORY_DB_SCHEMA` setting is present, it changes Oracle's current schema after checking that the value contains only allowed identifier characters. This supports a restricted login account that accesses tables owned by another schema.

Run the program from the project root so the relative path `config/application.properties` resolves correctly. Never commit that real settings file; `.gitignore` excludes it.

#### `dao/InventoryDao.java`

DAO means **Data Access Object**. This class contains the SQL used by the application. It:

- Reads users, roles, products, categories, suppliers, stock, and history.
- Inserts or updates products and other records.
- Creates and updates user accounts.
- Records stock movements.
- Converts Oracle result rows into Java model records.
- Closes connections and SQL objects after use.

Most values supplied by a person are passed through `PreparedStatement` parameters (`?`) instead of being joined into SQL text. This helps prevent SQL injection and handles values safely.

The `record(...)` method uses an explicit database transaction. It locks the chosen product row with `SELECT ... FOR UPDATE`, checks available stock for an `OUT`, inserts the movement, and commits. If something fails, it rolls back. The lock makes two simultaneous stock-outs for the same product wait their turn, preventing both from spending the same units.

### Business rules and login

#### `service/InventoryService.java`

This layer is the rule checker between the UI and the DAO. For example, it checks that quantities are positive and fit the database's number size, text fields are not too long, dates are in the right order, emails look reasonable, and the caller's role is allowed to perform an action.

Before protected actions, `require(...)` asks Oracle for the user's current active role. The role stored in the session alone is not trusted forever: a disabled user or changed role must sign in again. Hiding a button in the UI is useful for clarity, but the service check is the real application permission check.

#### `security/PasswordHasher.java`

Passwords are not stored as readable text. This class uses PBKDF2-HMAC-SHA256, a random salt for each password, and many rounds of calculation to create a stored hash. At sign-in it repeats the calculation and compares the result. The random salt means equal passwords do not produce equal stored hashes.

### Data model objects

#### `model/InventoryData.java`

This file defines simple records that carry data between layers:

- `Category`: category ID, name, description, and active status.
- `Supplier`: supplier ID and contact details.
- `Product`: SKU, name, description, category/supplier IDs, unit, reorder level, and active status.
- `StockRow`: product details plus calculated quantity and low-stock status.
- `TransactionRow`: one stock movement and its product/user labels.
- `UserRow`: username, role, and active status.

These records are not the database itself. They are Java-shaped copies of information read from Oracle or ready to be saved there. `BigDecimal` is used for quantities so decimal amounts are not subject to ordinary floating-point rounding errors.

#### `model/Role.java`

The Java role names are `ADMIN`, `INVENTORY_STAFF`, `VIEWER`, and `SUPPLIER`. They correspond to the labels in Oracle's `app_role` table. Admins link each Supplier user to one supplier record; supplier sessions carry that authenticated association for scoped reads.

#### `model/Session.java`

After successful sign-in, a `Session` holds the user's ID, username, and role for the current run of the program. It is passed to the service layer so actions can be checked against that identity.

### User interface

#### `ui/LoginFrame.java`

This is the sign-in window. It reads the username and password, sends them to `InventoryService.login(...)`, clears the password box afterward, and either shows an error or opens `AppFrame`.

#### `ui/AppFrame.java`

This is the main window. It creates tabs for current stock, products, and transaction history. Admin users also see category, supplier, and user-management tabs. Inventory Staff and Admin users can record stock movements; Viewers can look at data but cannot change it.

The frame calls service methods to load data and builds Swing tables from the returned model objects. Forms collect product, category, supplier, user, and stock-movement values. A successful save triggers a refresh so the latest Oracle data appears on screen.

Database work is run with `SwingWorker`, away from Swing's event thread. This prevents the window from freezing while Oracle responds. When the background task finishes, the UI thread displays the result or an error message.

## 5. Oracle database design

The SQL files define the structure Oracle stores. Tables hold rows; primary keys identify rows; foreign keys connect related rows; unique rules prevent duplicates; check rules reject invalid values; sequences generate numeric IDs.

| Table | What one row represents | Important links |
|---|---|---|
| `app_role` | A role name such as Admin or Viewer | Referenced by `app_user` |
| `app_user` | An application login and password hash | Has one role; referenced by stock movements |
| `category` | A product group | Referenced by `product` |
| `supplier` | A supplier and its contact details | Referenced by `product` |
| `product` | A stock-keeping item with SKU, unit, and reorder level | Has one category and one supplier; referenced by movements |
| `stock_transaction` | A stock-in or stock-out event | Links one product and one user |

The relationships are:

```text
app_role 1 ── many app_user
category 1 ── many product
supplier 1 ── many product
product  1 ── many stock_transaction
app_user 1 ── many stock_transaction
```

The schema uses one primary supplier per product. Stock is **not** stored as a number on the product row. Instead, it is calculated from the movement history:

```text
current stock = total quantity of IN movements - total quantity of OUT movements
```

This keeps a history of why the stock changed. For example, an `IN` movement of 20 followed by an `OUT` movement of 3 gives current stock of 17. Each movement stores its type, positive quantity, time, user, and optional reference/note.

### Database protections

- Primary keys keep each row's ID unique.
- Foreign keys stop a product from referring to a missing category or supplier, and stop a movement from referring to a missing product or user.
- Unique indexes make usernames, category names, supplier names, and SKUs unique without regard to letter case.
- Check constraints allow only `IN` or `OUT`, require positive quantities, and prevent negative reorder levels.
- Database sequences generate IDs for users, categories, suppliers, products, roles, and movements.
- Indexes help Oracle find products and transactions more efficiently.

## 6. SQL setup files

### `database/schema.sql`

Creates the sequences, tables, indexes, and constraints. It is for a **new, empty schema**. It is not a reset script and should not be rerun over tables that already exist.

### `database/seed.sql`

Adds four fixed role names: Admin, Inventory Staff, Viewer, and Supplier. It does not add products, categories, suppliers, or users. It is a simple insert script, not an idempotent script; running it again after the roles exist causes duplicate-key errors. Those errors mean the role rows already exist, not that the database should be recreated.

### `database/runtime_grants.sql`

Shows object grants needed by a restricted runtime account or role: read/write access on selected application tables and permission to use sequences. Replace `INVENTORY_RUNTIME` with the account/role name before running it as the schema owner. The grant script does not create that Oracle user or role. The application's database login must be a user account; a role by itself cannot log in.

## 7. Important workflows

### First-time setup

1. Create or choose an Oracle PDB and schema owner.
2. Connect to that PDB as the schema owner and run `database/schema.sql`.
3. Run `database/seed.sql` once to add the role names.
4. Copy `config/application.properties.example` to `config/application.properties` and set the actual URL, username, and password. For Oracle XE from this project, the service URL may look like `jdbc:oracle:thin:@//localhost:1521/XEPDB1`; use the service name configured on your computer.
5. Build with `mvn package` from the project root.
6. Run `java -cp target/inventory-stock-manager-1.0.0.jar edu.inventory.BootstrapAdmin` in a real terminal and create the first Admin.
7. Start the desktop app with `java -jar target/inventory-stock-manager-1.0.0.jar`.

### Sign-in flow

1. `LoginFrame` gets the username and password.
2. `InventoryService.login` checks that input is present and calls `InventoryDao.login`.
3. The DAO finds an active matching username and reads its stored hash and role from Oracle.
4. `PasswordHasher.verify` checks the entered password against the stored hash.
5. On success, Java creates a `Session` and opens `AppFrame`, or `SupplierFrame` when the role is Supplier.

### Supplier accounts and portal

An Admin creates Supplier logins in the Users tab. Choose the Supplier role and an active supplier; the service rejects missing or inactive associations. Passwords use the same PBKDF2-HMAC-SHA256 mechanism as all other users. Supplier stock and activity queries include the session supplier ID in the DAO. Apply `database/migrations/add_supplier_login.sql` once to an existing database; fresh installs include the relationship in `database/schema.sql`. To check isolation, create two suppliers with products and separate logins, then confirm each sees only its own products and movements.

### Recording stock-in or stock-out

1. An Admin or Inventory Staff member opens the movement form and chooses a product, `IN`/`OUT`, and quantity.
2. `InventoryService` checks the role and that the quantity is positive and fits the supported precision.
3. `InventoryDao.record` locks the product row. For an `OUT`, it calculates current stock and rejects a quantity larger than what is available.
4. The DAO inserts a transaction with the signed-in user's ID and Oracle's current timestamp, then commits.
5. The UI refreshes current stock and transaction history. The total is recalculated from the movement rows.

### Adding a product

An Admin or Inventory Staff member enters the SKU, name, category, supplier, unit, and reorder level. The service validates the text and numeric values. The DAO inserts the product using `product_seq`. A product requires an existing category and supplier because Oracle enforces both foreign keys.

## 8. Maven, JAR files, and generated files

`pom.xml` tells Maven the project name/version, Java release (17), dependencies, and build plugins. The Oracle JDBC driver is a runtime dependency. Maven compiles the Java source and the Shade plugin puts the driver into a runnable JAR and writes `edu.inventory.Main` as its starting point.

- `mvn package` compiles and packages the program.
- `target/` contains generated classes and JAR files. It can be recreated by Maven and is ignored by Git.
- `dependency-reduced-pom.xml` is generated by the Shade plugin. It is not Java source code.
- `java -jar target/inventory-stock-manager-1.0.0.jar` launches the normal UI.
- `java -cp target/inventory-stock-manager-1.0.0.jar edu.inventory.BootstrapAdmin` launches the separate first-Admin setup.

The Shade warning about duplicate files means that multiple dependency JARs contain a file with the same path. The plugin keeps one copy while making the combined JAR. A build that ends with `BUILD SUCCESS` completed successfully; investigate further only if the app itself shows a real problem.

## 9. Git and private settings

`.gitignore` excludes `target/`, editor project files, logs, and `config/application.properties`. The example configuration is safe to share because it contains placeholders. Before pushing to GitHub, use `git status` and confirm the real properties file and generated JARs are not staged. Do not put Oracle passwords in source files, commits, screenshots, or public repositories.

## 10. Current limits of the project

- Oracle is required; there is no built-in fake or offline database.
- Supplier users have read-only access to their own products, calculated stock, related activity, and profile.
- A product has one primary supplier.
- Stock movements cannot be edited or deleted through the app. Product deletion is allowed only when there is no movement history; otherwise an Admin can deactivate the product.
- Stock-outs cannot reduce stock below zero.
- There are no purchase orders, sales, prices, revenue, payment tracking, supplier portal, or automatic sample products in the schema setup.
- `seed.sql` creates role names only. Sample inventory requires separate category, supplier, product, and stock-movement rows.

## 11. Short glossary

| Term | Plain meaning |
|---|---|
| Schema | A collection of database objects belonging to an Oracle owner account |
| Table | A structured place where Oracle stores rows of one kind |
| Row | One saved item, such as one product or one movement |
| Primary key | The unique ID for a row |
| Foreign key | A rule linking a row to a real row in another table |
| Sequence | An Oracle number generator used for new IDs |
| JDBC | The Java interface used to send SQL to a database |
| DAO | Java class whose job is to read and write database data |
| Transaction | A group of database changes that are saved together or rolled back together |
| Role | A set of application permissions, such as Viewer or Admin |
| Hash | A one-way password result stored instead of the original password |
| PDB/service name | The Oracle database service name in the connection URL, such as `XEPDB1` |
